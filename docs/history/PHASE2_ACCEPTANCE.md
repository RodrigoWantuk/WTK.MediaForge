## Current Product Interpretation

Phase 2 established important contracts, but product readiness is now decided by
composite hardware proof results, not by the historical phase checklist.

Current Windows product proof status:

- MP4 recording product path: passed when the report shows hardware H.264 encode,
  render-to-encode, and MP4 packet proof all passed.
- RTMP H.264 product path: passed when the report shows hardware H.264 encode,
  render-to-encode, and RTMP network proof all passed.
- Hardware H.264 decode: passed when the report shows Media Foundation/D3D11VA
  returns a decoded GPU texture.
- MP4 video input: passed when hardware decode, decode-to-render, and MP4 input
  product proofs all pass through the normal Windows provider route.
- Webcam input: passed when the Windows webcam proof shows Media Foundation
  capture, immediate D3D11 upload, bounded `KeepLatest` GPU slot lifetime, and
  Vulkan render validation.
- NDI input/output: Windows Standard SDK runtime detection and source discovery
  exist, but video product paths remain blocked until GPU-safe input/output
  proofs are approved.

## Blocking Rules Still Verified

- No software decode/encode fallback for continuous video.
- No uncompressed continuous video frames in CPU/RAM on product paths.
- No `CpuReadbackSink` as recording, streaming, or primary preview.
- No FFmpeg/libx264/libx265 in the native MP4/RTMP hardware product paths.
- Sinks consume completed outputs or encoded packets; they do not trigger render.

## Readiness Labels

Use `MediaForgeSupportStatus`, `ProductReadinessStatus`, and the media proof
report instead of old phase labels. A feature is product-supported only when its
required composite proofs are `Passed`. Hardware absence, unsupported driver
capabilities, or missing interop must be reported as explicit `Unavailable` or
`Blocked` with a reason.
